# Security and trust model

This is DRAW's trust model: what each party and each credential can and can't do on the ledger, what the demo server could fake, how sign-in handles an LP's token, and what a production deployment would change. It describes the code as it runs today, including where the demo is weaker than production would be. The contracts and parties are in [ARCHITECTURE.md](ARCHITECTURE.md), and everything not built or shown yet is in [LIMITATIONS.md](LIMITATIONS.md).

## Powers on the ledger

| Party | Can | Cannot |
|---|---|---|
| Fund (its admin party) | Invite investors. Name a verifier party when it creates a fund. Issue calls up to each LP's remaining commitment, which also sends each LP a payment request. Withdraw a payment request. Match a payment (`Obligation_MarkPaymentPending`). Settle with a matching allocation. Mark overdue after the due time. Send to review, reopen, put an obligation back to awaiting payment when the payment it was waiting on was withdrawn or expired, waive an overdue or reviewed obligation, each with a note | Create an obligation without the LP's signature. Mark anything funded without executing a matching transfer. Settle twice. Mark overdue early. Close another obligation's payment request when settling or waiving. Read any other fund's or party's contracts |
| LP | Accept or decline its invitation. Read its own payment request and reject it, which leaves the obligation open. Create allocations from its own holdings, from that request or with the reference set directly. Withdraw its own allocation any time before it is executed | See any other LP's commitment, obligation, payment request or allocation. Change its own obligation. Withdraw a payment request. Settle anything |
| Unrelated party | Nothing on DRAW contracts | Read or act on any DRAW contract |
| Read-back user (the verifier's ledger user) | Read as the fund | On LocalNet, submit anything (HTTP 403, checked in every LocalNet canonical run). On DevNet the verifier client NODERS issued for DRAW holds read rights on the fund's party `draw-admin` and nothing else ([probe 20261007T125624Z](../evidence/devnet/probes/20261007T125624Z/result.json)), and the ledger refused it when it tried to submit as the fund ([run 20261007T125638Z](../evidence/devnet/runs/20261007T125638Z/result.json)). It could also act and read as the team's personal wallet party until NODERS removed that right on 2026-10-07 ([probe 20261006T133219Z](../evidence/devnet/probes/20261006T133219Z/result.json)), and the live server has read back through it since about 13:00 UTC that day |
| Backend client user (DevNet) | Act for the five demo parties, and read as the fund's party `draw-admin` | Act or read for any other party, the team's personal party, a signed-in LP's party and the external parties included ([probe 20261007T125624Z](../evidence/devnet/probes/20261007T125624Z/result.json)) |
| Verifier party (package 0.3.0, optional, Daml Script only) | Read the fund that names it, every call and every obligation, including the settlement record | Act on the obligations or the fund (refused in `test_verifier`). See commitments, invitations or payment requests |
| Token registry (the DSO) | Per the Splice token design, see every Amulet allocation and holding, including the settlement reference. Not checked in any run | Per the same design, see the obligation contract or anything outside the token flow. Not checked in any run |
| Scan, the network's explorer | Per the Splice Scan API docs, show the Canton Coin leg of each payment with its random reference and the party ids, whose hints such as `draw-lpa` are readable. Inferred from the docs and not checked against Scan | Show the notices, per the same docs |
| Participant operator | Read every party hosted on its participant. Grant ledger rights on those parties, as NODERS did for DRAW's clients | Act for an external party without that party's signature (the LocalNet custody run, and on DevNet [run 20261007T130259Z](../evidence/devnet/runs/20261007T130259Z/result.json), where the ledger refused the run's login acting for LP A without LP A's key) |

Waiving is a real power of the fund. A waived obligation leaves the unresolved total. It always carries a note, and the LP sees that it was waived.

## Who creates parties and who signs

- LocalNet: the participant's `ledger-api-user` allocates parties and creates one ledger user per party with `actAs` and `readAs` on that party only. The read-back user gets `readAs` on the fund only.
- DevNet, on the HackCanton node: the team created the five demo parties in the node's Console, where the team's hackathon login (Keycloak password grant) acts for all of them. On 2026-10-06 NODERS issued DRAW three Keycloak clients: a public web client for sign-in, a backend client and a verifier client. The live server and run 20261007T125638Z act for the demo seats through the backend client, with client-credentials tokens, and read back through the verifier client, which the live server has held since about 13:00 UTC on 2026-10-07. The team's personal login is no longer on the server. Run 20261006T131900Z used the same two clients. The DevNet runs before it, and the live site before about 13:25 UTC on 2026-10-06, used the team's login for every seat. A node that offers a participant-admin user or one OAuth client per role is also supported, through [provision.mjs](../scripts/demo/provision.mjs).
- DevNet, external parties: a team can't allocate them on this node, so DRAW generated a key and signed an onboarding transaction for each of five parties, and NODERS allocated them on 2026-10-07 (`b94ab230-ext-1` to `-ext-5`: the fund, LP A, LP B, LP C and an unrelated party). In [run 20261007T130259Z](../evidence/devnet/runs/20261007T130259Z/result.json) (`DRAW_PARTY_MODE=external-provisioned`) the node prepared each transaction and the acting party's own Ed25519 key signed it. One login, the team's own, submitted for every party and read each settlement back. The ledger refused it acting for LP A without LP A's key, and refused LP B's key signing for LP A. All five keys sat on the machine that ran the script, so this shows that the ledger needs each party's signature. It doesn't show that separate people held the keys. The live site doesn't use these parties.
- DevNet, an LP that signs in with HackCanton: its party is its own login's wallet party, and its browser signs every one of its actions with its own token. The server invites that party and never acts for it ([Sign in with HackCanton](#sign-in-with-hackcanton-devnet)).
- Non-custodial mode (`DRAW_PARTY_MODE=external`, LocalNet): each party is an external party with its own Ed25519 key. The participant prepares each transaction, the party's key signs it, and the participant executes it. The server's ledger user is refused when it tries to act for the party.
- Token actions: the LP's ledger user submits `AllocationFactory_Allocate`, either from its payment request's settlement and leg, the way a Token Standard wallet would, or with the obligation reference set directly. The fund's ledger user submits `Obligation_Settle`, which exercises `Allocation_ExecuteTransfer` using the authority the LP gave when it co-signed the obligation. That authority is usable only inside `Obligation_Settle`, after every correlation check passes.

## What the application server can and cannot fake

In the demo, the app server ([app/server.mjs](../app/server.mjs)) holds a working credential for every demo seat. On LocalNet the HS256 secret is `unsafe` and documented, so the server could mint a token for any user. On the DevNet node it holds the backend client, which acts for the five demo parties and nothing else, and since about 13:00 UTC on 2026-10-07 the verifier client, which only reads as the fund. The team's personal login was removed from it at about 13:25 UTC on 2026-10-06, and the verifier client was added only after NODERS removed its right to act for the team's personal party, so nothing the live server holds can act for a signed-in LP's party. It never receives that LP's token either. The live API answers only the web app's proxy, which adds a service token, and refuses any action without the demo access code.

So the demo server could submit as a demo LP, which in production it must not be able to do. It can't make an obligation funded without a real allocation from that LP executed on the ledger, can't make the ledger show LP B's obligation to LP A, and can't make a consumed allocation usable again. The app shows a notice as funded only when the ledger says `Funded` and the read-back step has written a `VERIFIED_FUNDED` receipt for it. A forged receipt file alone does nothing to ledger state, and the proof scripts re-read the ledger themselves.

## Sign in with HackCanton (DevNet)

An LP with its own HackCanton login can join a demo fund as itself, when the API runs with `DRAW_SIGN_IN=true`. Every run of it signed in with the team's own login as the LP. In the earlier runs the server also held that login, so the server's credential could have acted for that party, and those runs show DRAW didn't need it to: the LP's reads, its acceptance and its payment came from its browser with its own token. In the six newest runs the server held the backend client, and in the two newest, [paying from DRAW](../evidence/devnet/browser/web-hackcanton-20261007215349/) and [paying with Accept in the node's wallet](../evidence/devnet/browser/web-hackcanton-wallet-20261007215129/), it also held the verifier client for the read-back. Neither can act for that party, so the same person held both sides with different credentials. Separate people still need a second person's login.

- Token handling: the browser runs the OIDC authorization code flow with PKCE against the node's Keycloak, with DRAW's own public web client `xidoncapitals-web-app-hackcanton-01-devnet`, which NODERS issued with the live site's origin and `localhost:3100` as web origins. The first four sign-in runs used NODERS' public web-app client `web-app-ui-hackcanton-01-devnet`. The code verifier and `state` stay in the tab during the redirect, and the callback refuses a sign-in that didn't start in that tab. The token and refresh token sit in that tab's `sessionStorage`, so they end with the tab or with Sign out. Sign out also ends the Keycloak session with the refresh token, and every sign-in asks for the password (`prompt=login`), so on a shared browser the next person never comes in as the last one. Only Keycloak refusing the refresh token, or the JSON Ledger API answering 401, ends the sign-in. A refresh that can't reach Keycloak keeps it for the next try, a 401 from the wallet's API is a refusal, and a refresh that lands after Sign out is dropped. [signin.test.mjs](../scripts/test/signin.test.mjs) covers each of these. The site loads no third-party scripts, but anything that runs in that tab could use the token. The token goes only to the node: its Keycloak, its JSON Ledger API and its validator API. Those addresses come from the API's `/api/config`, so they are only as right as the API's settings.
- What the server learns: the LP's party id, which the `join` action sends, and what the fund manager party already sees, which is the LP's commitment, its notices and the payments addressed to the fund. The server keeps DRAW's own record per notice, the read-back receipt and logged steps, and hands only that to the LP's browser at `GET /api/record?ref=`.
- Why `join` with any party id is harmless: it only makes the fund manager invite that party. An invitation does nothing until that party accepts it with its own credential, and a payment request only exists for an obligation, which needs an accepted commitment. `join` refuses the demo seats' parties, takes one signed-in LP per demo fund, needs the demo access code, and counts toward the action rate limit. Closing the demo fund withdraws an invitation nobody accepted.
- Closing a demo fund, on start over or when the API forgets the tour, also withdraws its open payment requests as their executor, so no LP's wallet keeps offering that fund's notices. The LP takes back its own locked coin in its wallet.
- The fund manager seat acts through the backend client, like every demo seat. Sign-in for the fund manager seat isn't built.

## Production authentication (not built, apart from LP sign-in on the HackCanton node)

- Each person signs in through the fund's or the LP's identity provider and gets a token for their own ledger user only.
- The app server holds no LP credentials. LP payments are signed by the LP's own wallet or participant, for example through a CIP-0103 wallet provider.
- Each LP is hosted on its own validator or by a provider it trusts, so no single participant operator can read all LPs.
- The fund's operations users sign its settle and resolve actions, each with their own login, and no shared service account acts for the fund.

## Settlement correlation

- Each obligation reference is `DRAW-` plus 16 random hex characters, unique within a call (checked by `Fund_IssueCall`) and random across calls.
- `Obligation_Settle` requires the allocation's settlement reference id and transfer leg id to equal the obligation reference, the executor and receiver to be the fund's party, the sender to be the obligated LP, the instrument to match, and the amount to equal the amount due. It then checks that every receiver holding is owned by the fund's party, in the right instrument, and that they sum to the amount due.
- If two obligations ever shared a reference, LP, amount and instrument, one allocation could settle either, but only one, because execution consumes it.
- Each payment request names the same reference, payer, receiver, amount and instrument as its obligation, so an allocation made from it passes these checks unchanged. `Obligation_Settle` and `Obligation_Waive` archive the request when given its id, and refuse a request that belongs to another obligation.

## Replay and duplicates

- Ledger: an executed allocation is archived. Presenting it again fails with contract not found. A funded obligation refuses another settlement. Both are tested on LocalNet and in the campaign, and the replay is refused on DevNet too.
- Read-back step: it also refuses an update id it already used for a different obligation, and refuses any update that doesn't itself settle the claimed obligation. Its memory of used update ids lasts only for the process. The ledger protection doesn't depend on it.
- A second matching payment after funding is classified `duplicate`, and the LP withdraws it.

## Stale state

Every state change archives the obligation and creates a new contract id. An action against a stale contract id fails with contract not found. Reads retry until the expected state appears. Nothing is cached between requests except the session's party list.

## Frontend compromise

The browser calls the web app on Cloudflare, which proxies `/api` and `/evidence` to the API with a service token. A signed-in LP's browser also calls the node directly with its own token. A compromised frontend can show wrong numbers on that screen. It can't change ledger state beyond what the server's credentials allow, plus, in a tab where an LP signed in, what that LP's login allows. The `/proof` page and evidence files are produced by scripts that read the ledger directly.

## Secrets

- `.env` is gitignored. [.env.example](../.env.example) lists names only.
- LocalNet's `unsafe` secret is public and only valid on LocalNet.
- The party keys of the scripted runs, on LocalNet and for the DevNet external parties, stay in the gitignored `.keys/` folder on the machine that ran them.
- DevNet client secrets go in the API's `.env`, never in the repository: `DRAW_BACKEND_CLIENT_SECRET` and `DRAW_VERIFIER_CLIENT_SECRET` for the clients NODERS issued, or one per role on a node that issues those. The public web client has no secret.
- Private planning notes are kept out of the repository.
- `DRAW_SERVICE_TOKEN` lives in the API's `.env` and as a Worker secret. The Cloudflare build blanks every non-public variable and scans its output for secret values before deploying ([web/scripts/cloudflare.mjs](../web/scripts/cloudflare.mjs)).
- On 2026-10-06, gitleaks 8.30.1 and a check for every value in `.env` found no secret in the 45 commits up to `94ffc14`. The same day, gitleaks found nothing in the files not yet committed (modified or untracked, outside ignored paths), and the only sensitive `.env` value in them is LocalNet's public `unsafe` secret. The 31 commits made after `94ffc14`, 76 in all at `13a3bcb` on 2026-10-07, haven't had that scan. Re-run both checks on the release commit at the freeze and record its id and date here.

## Demo role switcher

The seat chosen at onboarding, and "Switch seat", decide which party every query and action runs as. On LocalNet that means a different ledger user per party. On DevNet the backend client queries as the chosen demo party, and the screens say so. An LP that signs in with HackCanton queries with its own token instead. The demo seats are a demo convenience. A sign-in system for every seat is in the production model above.
