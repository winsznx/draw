# How to check the claims

Every result below was written by a script. Each row says where it is and how to reproduce it. LocalNet and DevNet results are kept apart.

This page is for judges and reviewers who want to check what DRAW says instead of taking it on trust. The claims themselves, each with its network and its limits, are in [claims.yaml](../claims.yaml), which is the ceiling for everything the README, the app and the pitch may say. The quickest way in is the proof page on the live site, https://drawcalls.xyz/proof, which renders the same result files and needs no access code.

Results come from three places. Daml Script is the Daml test runner, with no network. LocalNet is Splice LocalNet 0.8.4 on one machine, settling in Amulet. DevNet is the HackCanton shared node that NODERS runs for the hackathon (Canton 3.5.19, Splice 0.8.4), settling in Canton Coin from the DevNet faucet. Neither token has monetary value, and every dollar figure is the scenario. A notice, in this page, is the `CapitalCallObligation` contract that [claims.yaml](../claims.yaml) and the evidence files call an obligation. Other fund and Canton words are defined in [the glossary](README.md#words-used-in-these-docs).

## The proof chain

For a capital call to count in DRAW, this chain has to hold, in order:

1. The fund issues the call.
2. Each LP gets a private notice, a contract between the fund and that LP that no other LP or unrelated party can read, though the operator of the node that hosts them can.
3. The LP pays through the Token Standard and the fund settles. The payment carries the notice's reference, and the notice turns funded in the same transaction that moves the money.
4. A read-back step reads the settlement back from the ledger and runs 14 checks.
5. Only then does the notice count as verified funded.
6. The fund's deployable figure is recomputed from verified notices.
7. The LP that didn't pay stays unresolved.

The table shows what binds each step and where to see it in the two canonical runs. The [scripted DevNet run 20261007T130259Z](../evidence/devnet/runs/20261007T130259Z/result.json) is on package 0.3.0, on the HackCanton shared node, and there each of five external parties signs with its own key. All five keys sat on the machine that ran it, and one login, the team's own, submitted for every party and read each settlement back. The [LocalNet custody run 20261004T183146Z](../evidence/local/runs/20261004T183146Z/result.json) is on package 0.2.0, and there each party signs with its own key too. On DevNet one login reads for every party in each run, the team's own in this one, so DRAW picks which party it reads as, and the DevNet rows show party-scoped reads and transaction streams. Each LP reading with its own separate login is shown on LocalNet.

DRAW keeps the execution of a payment apart from its verified outcome. A payment moves through these stages, and only the last one counts as money: ACTION_REQUESTED (the LP was asked to pay), ACKNOWLEDGED (a matching payment is locked for the fund), TRANSFER_EXECUTED (the fund executed the transfer), SETTLEMENT_OBSERVED (the read-back step read the settlement), CLAIMED_FUNDED (the ledger says `Funded` and the read-back hasn't confirmed it yet) and VERIFIED_FUNDED (the receipt passed all 14 checks). A receipt that fails any check is CONTRADICTED. A submitted transaction, a signature or a hash on its own is never funded.

For DevNet it shows the newest scripted run that passed every check, now the own-keys run 20261007T130259Z, with how it signed, its privacy matrix, read-back receipts, totals and refusals, and the newest run of each live browser journey, passed or not, with its steps, screenshots and recorded setup: the demo-seat journey, the LP that approves in its Canton Coin wallet, and the LP that pays from DRAW. The own-keys run skipped that check, so the page says the read-back read as the same ledger user as the seats.

## Reading a receipt

A receipt, such as [receipt-lpA.json](../evidence/devnet/runs/20261007T130259Z/receipt-lpA.json), is what the read-back step wrote after reading one settlement back from the ledger. Its `verdict` is `VERIFIED_FUNDED` only if every one of its 14 checks passed, and `CONTRADICTED` otherwise. The checks run in this order:

| # | In plain words | Recorded as |
|---|---|---|
| 1 | The settlement's update id wasn't already used as evidence for another notice | `update id not already used as evidence` |
| 2 | The notice is in the fund's records under its reference | `obligation found in admin ACS by reference` |
| 3 | The update is a transaction | `claimed update is a transaction` |
| 4 | It exercises `Obligation_Settle` | `update exercises Obligation_Settle` |
| 5 | The same transaction executes the referenced allocation | `same update executes the referenced allocation` |
| 6 | That execution consumed the allocation, so it can't be used again | `allocation execution consumed the allocation` |
| 7 | It creates the funded notice for this reference | `update creates the funded obligation for this reference` |
| 8 | The settlement record names the holdings the fund received | `settlement record names receiver holdings` |
| 9 | The fund's current notice is that funded one | `current admin ACS obligation is the funded one` |
| 10 | Those holdings are active | `receiver holdings are active in admin ACS` |
| 11 | They're owned by the fund | `receiver holdings owned by fund admin` |
| 12 | They're in the expected instrument | `receiver holdings are the expected instrument` |
| 13 | The received amount equals the amount due | `received amount equals amount due` |
| 14 | The payer is the LP that owed it | `payer is the obligated LP` |

The receipt also records `stateBefore` and `stateAfter` (PaymentPending and Funded), the amount due, the amount received, the notice's reference, `recordTime`, the ledger's time for the settlement, and `verifiedAt`, the time on the read-back step's clock when it finished. Each canonical run also keeps `receipt-replay-attempt-lpB.json`, where LP A's settlement was offered as evidence for LP B. Its verdict is `CONTRADICTED`, with checks 1, 7, 9 and 14 failing ([DevNet](../evidence/devnet/runs/20261007T130259Z/receipt-replay-attempt-lpB.json), [LocalNet](../evidence/local/runs/20261004T183146Z/receipt-replay-attempt-lpB.json)).

Who did the reading differs by network and run. On LocalNet the read-back step uses a separate ledger user with `readAs` on the fund only, and every LocalNet canonical run checks that it can't submit. In DevNet run [20261007T125638Z](../evidence/devnet/runs/20261007T125638Z/result.json) the read-back used the verifier client NODERS issued for DRAW, which can only read as the fund ([probe 20261007T125624Z](../evidence/devnet/probes/20261007T125624Z/result.json)). That run checks that it can't submit as the fund, and that each receipt was read as the verifier's own ledger user. The live site has read back on the same client since about 13:00 UTC on 2026-10-07, and through the backend client before that. Run [20261006T131900Z](../evidence/devnet/runs/20261006T131900Z/result.json) read back on that client too, while it could still act and read as the team's personal wallet party ([probe 20261006T133219Z](../evidence/devnet/probes/20261006T133219Z/result.json)), a right NODERS removed on 2026-10-07. The client can't read as an external fund party, so the canonical DevNet run, the own-keys run [20261007T130259Z](../evidence/devnet/runs/20261007T130259Z/result.json), read back with the team's login, the same one that submitted for every party, and skipped the submit check with its reason. The DevNet runs before the NODERS clients used one shared hackathon login and skipped that check too. `verifierUser` in each receipt records the subject of the token the read-back's reads carried. `readAs`, recorded in the DevNet receipts from 2026-10-06 on, shows which party it read through, the fund's own party. Package 0.3.0 lets a fund name a verifier party for the read-back to read through instead. That party's view is tested in Daml Script only, and no ledger run has read back through it yet. In every case the read-back step runs in the same process as the submitter, so DRAW doesn't call it independent.
